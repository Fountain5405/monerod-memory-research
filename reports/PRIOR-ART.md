# Prior art: what the Monero developers already did about FCMP++ verification memory

Written 2026-11-03 at the owner's question "has this kind of improvement been floated by anyone in the monero dev community yet?". Sources are public GitHub issues, pull requests and release notes (read-only; nothing was posted). Everything measured in this repo was done on v0.19.0.0-beta.3.1, which already contains all of the upstream work below.

## Short answer
The problem is known and was worked on in October-December 2025. Upstream reduced the per-verification footprint inside monero-oxide (1.2 GB -> ~790 MB -> ~250 MB per 128-input proof), restructured monerod's batch verification to one batch per thread, and capped glibc's arena count. The remaining "250 MB x threads, never returned to the OS" shape was stated explicitly and accepted as the expected footprint. Two of our three changes were floated in those threads as ideas (a cap on concurrent heavy verifications; a size-aware thread policy with a 16-input split) but not built in the form we built them; the third, not storing the circuit at all (E007 / E017), and the removal of the O(c x q) fold, I did not find proposed anywhere.

## Timeline
- **2025-10-08, seraphis-migration/monero#147 "monerod killed by OOM while syncing"** (j-berman). Reports on 8 GB machines. Two causes separated: runaway block-download spans (Boog900's analysis of `stripe_proceed_main` / `get_next_needed_height`, later fixed in alpha.1.5 "Prevent runaway spans"), and verification memory. Closed 2026-03-25 as resolved.
- **2025-10-29, seraphis-migration/monero#202 "monerod OOM after synced"** (j-berman). On 2025-11-03 j-berman, using valgrind, found that **verifying one 128-input proof peaked at ~1.2 GB** and that threaded batch verification multiplies it; kayabaNerve cut it to 790 MB (monero-oxide#39, commit 96eae33: merge two loops in generalized-bulletproofs to drop a large carry-over allocation). kayabaNerve suggested "limiting all verifying threads to 128 inputs simultaneously at max" or, alternatively, "use a threadpool for all proofs of <= 16 inputs and only kick large proofs to their own thread". j-berman's branch `fcmp++-limit-verify-mem-usage` (max 128 inputs per active batch plus `mallopt`) stopped the OOMs on a 2-thread / 8 GB machine at the price of 2-3x slower sync. kayabaNerve also noted memory "growing without any leaks being detected", which is the glibc arena retention we measured in E004. Closed 2026-04-24 "should be solved".
- **2025-11-04, monero-oxide#136 "FCMPs has a variety of unnecessary/small allocations"** (kayabaNerve): proposes one contiguous `Vec` instead of many small ones and more `Iterator` use; open. This is the same observation as our heaptrack attribution (millions of small `LinComb` allocations), with a constant-factor remedy; it does not propose dropping the stored circuit.
- **kayabaNerve/monero-oxide commit 34dab26 "Use a BTreeMap for WCG"** (late 2025): its message says the prior commit "introduced an O(n) memory with a smaller constant than before and O(n^2) computation cost"; this commit keeps the smaller memory at O(n log n). This is the ~250 MB per 128-input proof that the beta ships. The per-commitment fold we found still dominant in E006 (`arithmetic_circuit_proof.rs:779-783` at 31c26d9, ~52% of sync CPU) is in this area of the code, so the memory work of that period traded some verification CPU, which E007/E017 then recover.
- **2025-12-16, seraphis-migration/monero#224 "verify 1 batch per thread + even the load by input count"** (j-berman, merged; `rctSigs.cpp` +78/-21). Quote: "A single call to `fcmp_pp::verify` can use up to ~250mb of RAM ... This PR assumes the user has at least `n_threads * 250mb` of RAM ... memory allocated and freed is not getting released back to the OS. `monerod` on systems that use the `glibc` memory allocator is expected to use a total of `n malloc arenas * 250mb` out of the box." `--max-concurrency` is respected. This is the `batchVerifyFcmpPpProofs` our E004c/E012 cap sits in.
- **2025-12-16, seraphis-migration/monero#229 / #228 "set max arenas glibc will use"** (j-berman, merged): `mallopt(M_ARENA_MAX, n_threads)`. Our E004d found that capping arenas further does not help, because two threads sharing an arena both peak inside it; the trim (E004e) is what releases them.
- **2026-01-08, release v0.19.0.0-alpha.1.5**: "Drastically reduce the memory footprint of FCMP++ verification and smarter multithreaded sync", "Limit glibc from using more memory arenas than threads", "Prevent runaway spans when downloading the chain from overloading memory", "Dynamically adjust the amount of blocks downloaded based on sync speed" (the adaptive sync size whose interaction with the levin limit is our E001 wedge).
- **2025-12-13, seraphis-migration/monero#266** (stianov): node reaching 10 GB in 10 minutes of FCMP block sync, fixed by the pre-alpha.1.5 branch. Shows the pre-fix scale.
- **2026-02-11, seraphis-migration/monero#293 "monerod unresponsive while verifying large blocks"** (nahuhh, open): the node stops answering RPC for 10 s to 2 min while verifying a 30 MB block; j-berman suspects DB resizing. We observed the same symptom during the heavy window (SUMMARY "The RPC server stops responding while 24 threads verify heavily").
- **monero-project/monero#11407 "FCMP++: verify FCMP++ proofs tooling"** (j-berman) and its review in xmrack/monero-review#1350: the review summary cites an upstream figure of "about 200 MiB per 128-input proof, multiplied by the thread count" as an unsettled peak-memory concern, to be settled with a running binary. Our measurements settle it for stressnet: 5.4-5.6 GB at 24 threads, scaling with thread count (E003).
- **Stressnet Monitor / data collection, seraphis-migration/monero#495** (open, 2026-10): a plan to find the minimum hardware for an FCMP++ node under load, tracking monerod RSS per host. Our min-cgroup method (E009/E013) answers the same question for sync.

## What is new here, as far as I can tell
1. **Not storing the circuit** (E007 streaming accumulator, or E017's one pre-folded constraint): upstream reduced the stored circuit's constant (1.2 GB -> 250 MB) and discussed contiguity (#136), but every version keeps the `q` constraints in memory before `verify`. I found no issue, PR or comment proposing to fold them as they are produced.
2. **Returning memory with `malloc_trim`** after heavy batches: upstream set `M_ARENA_MAX` and `mallopt` and accepted that "memory allocated and freed is not getting released back to the OS"; the trim is what makes the idle node drop from ~4.8 GB to ~1 GB.
3. **The adaptive cap** (physical cores only when the largest proof has >= 16 inputs): kayabaNerve's two suggestions in #202 (bound the inputs in flight; a 16-input split between a pool and dedicated threads) are the same idea; j-berman's branch built the first form and found it 2-3x slower on 2 threads; #224 shipped one batch per thread instead. Our form keeps SMT for small proofs and loses nothing on heavy ones (-9% wall).
4. **The O(c x q) verification fold** as ~52% of sync CPU and its removal: not discussed in the threads I found; the BTreeMap commit message shows the authors were aware of a memory/CPU trade in that code.

## Not checked
Matrix rooms (#monero-stressnet, #monero-dev) and IRC logs were not searched; a verbal proposal there would not show up here. The monero-oxide repository has no issue or PR matching "streaming", "fold" or "constraint" besides #136.

## Wallet sync (community note relayed by the owner, 2026-11-03)
A developer comment seen in the Monero community chat, relayed by the owner on 2026-11-03: beta.3.1 carries a roughly 6x wallet sync speedup, a pending subaddress PR is expected to give about another 2x, there is "lots of low hanging fruit", and the old stressnet spam wallets could sync in under a minute if done efficiently, against over an hour today. What this means for the wallet track here: the monero-wallet-cli measured in W002 is built from the beta.3.1 tree, so the 6x is already in the baseline; the comment is about speed, and W002 measures memory, but a faster scanner that pulls and parses larger batches raises the refresh-time transients that W001 flagged as the likely wallet peak, so wallet speed work upstream and wallet memory here can pull in opposite directions. The spam wallets (many owned outputs) are the case our fresh wallet does not cover; W002's fresh wallet exercises the scan path only.
